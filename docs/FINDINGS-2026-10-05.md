# Findings from live multi-AI testing, 2026-10-05

Recorded by the lead, Claude Code (claude-opus-5-5), from one working
session with the owner. Every number below was measured in this
workspace; nothing is taken from vendor claims unless a source is named.
Raw receipts are local only (`tmp/`, `coord/reports/`), not in Git.

## Summary

1. **Effort setting matters more than model speed.** GLM 5.3 generates at
   a steady 60 to 65 tokens per second at every effort level. "max" only
   makes it think longer: 437 s against 174 s at "high" on the same review,
   with no better result. Use "high" by default.
2. **Our setup is not what makes runs slow.** Time to first token was about
   4 s; tool execution took under 4% of agentic run time. One early failure
   came from a task that let the worker run `find /`, not from the model.
3. **On a real task, four of five models produced the same correct fix.**
   The difference was test rigour and speed, and GLM 5.3 at "high" won with
   the smallest thinking budget.
4. **Different companies' reviewers catch different things.** No single
   reviewer found every issue; each round of a second vendor found something
   real the first missed.
5. **Models are unreliable about name and product conflicts.** Two models
   called names "low conflict" that registry checks showed were taken by AI
   projects. Verify facts with tools, not memory.
6. **The tool's own gaps showed up only through use:** a false usage-limit
   alarm, a database first-open race, and no way to consult or review outside
   a worker task. The first two are fixed; the third is a planned feature.

## GLM 5.3 speed: setup versus model

Measured from OpenCode's own session records (`opencode export`).

| Run | Effort | Total | Thinking | Thinking tokens (approx.) |
|---|---|---|---|---|
| Docs review, 31 KB prompt | max | 437 s | 418 s | 24,000 |
| Same prompt | high | 174 s | 153 s | 10,000 |
| Same prompt | low | 45 s | 30 s | 2,000 |

- Review quality did not follow effort: "high" found a real issue that
  "max" missed; "low" was shallow.
- Agentic runs: JobStore run 1 spent 457 s in the model, 22 s in tools and
  141 s waiting for 25 steps to start (about 5 s each); the finishing run
  spent 6 s in tools. The 10-04 keyboard failure spent 128 of 175 s in one
  `find /` command. Task design, not GLM.
- GLM 5.3 Flash was unreliable: a one-word answer took 50 s (GLM 5.3:
  4.6 s), and a real review produced nothing in 768 s.
- Plan allowance matters as much as quality: OpenCode Go's premium models
  have small allocations (Kimi K3 about 490 requests a month, while one
  JobStore task used 25).

## What dogfooding revealed about the tool

| Finding | Status |
|---|---|
| The usage-limit detector matched the bare word "quota" in worker output, so a failed run recorded a false limit wall and auto-bench could pause a healthy agent. | Fixed (89202b4). |
| JobStore failed when several processes opened a new database at once, and a crash during setup left a file it refused forever. | Fixed (JobStore 2b). |
| `review` only works on a worker task; the lead could not consult an AI or review its own branch through the tool, so those calls left no ledger record. | Planned: an `ask` command and review of any branch. |

| Hand-made worktrees lacked the `.agentteam-worker` marker, so Git guards were off. | Race worktrees now get it; init should always add it. |

## Lead process lessons

- `pgrep -f` and `pkill -f` match their own command line; a waiting loop
  using them waits forever. It cost about six minutes of GLM time twice.
- Paths in this workspace contain spaces; quote every one.
- Read the time with `date` for log entries; one entry was off by 16 minutes.
- Direct vendor CLI calls are fine for one-off questions but leave no
  record; route real work through the flock.
